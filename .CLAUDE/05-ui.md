# Web interface (`web/`)

FastAPI + server-side HTML templates (Jinja2) + [htmx](https://htmx.org/) (vendored in
`web/static/htmx.min.js`, no CDN) for partial page updates without a reload.
No build step (no npm/webpack) — the only custom JS is `web/static/corner-picker.js` (vanilla,
zero dependencies), for manual card cropping on the Grading page (see
07-grading.md). Text/notifications in the templates are in Italian, comments in the Python code
in English — the same convention as the old TUI.

## `web/app.py`

Creates the `FastAPI` instance, uses a `lifespan` to create/close the shared `AppState` (see
[02-architecture.md](02-architecture.md)), mounts `web/static/` at `/static`, and includes the 5
routers (`collection`, `add_card`, `bulk_add`, `grading`, `sell`).

## `web/deps.py`

Two dependencies shared by all routers:
- `templates` — a `Jinja2Templates(directory="web/templates")` instance.
- `get_state(request) -> AppState` — reads `request.app.state.ygo`, used as
  `Depends(get_state)` in handler signatures.
- `render(request, name, context)` — wrapper around `templates.TemplateResponse(request, name,
  context)`. **Note**: in recent Starlette versions, `TemplateResponse`'s signature requires
  `request` as an explicit first positional argument (no longer inside the context dict
  as in older versions) — if a future Starlette upgrade breaks this signature again,
  this is the only place to fix, since all routers go through it.

## `web/state.py` — `AppState`

The state shared across the whole app, a single instance per process (see
[02-architecture.md](02-architecture.md) for why this choice was made). Contains:
- `api` (`YGOProDeckAPI`), `cardtrader` (`CardTraderAPI`), `storage` (`StorageService`),
  `grader` (`CardGrader`) — the same service instances that in the TUI lived on
  `YGOValuerApp`.
- `collection: List[CollectionItem]` — loaded from disk at startup, mutated in memory.
- `bulk_queue`/`bulk_index` — state of the Bulk Add flow (list of `BulkQueueItem`).
- `pending_gradings: List[PendingGrading]` — **all** graded cards (single photo or bulk) not
  yet linked to a card in the collection, an "inbox" shared by both Grading flows
  (see [07-grading.md](07-grading.md)). `add_pending_grading`/`get_pending_grading`/
  `remove_pending_grading` are the only points that touch it. **Persisted** to
  `config.DEFAULT_PENDING_GRADINGS_FILE` (`pending_gradings.json`, images included as base64
  JPEG) — survives a server restart, unlike `bulk_queue`. See
  [07-grading.md](07-grading.md) for why this choice was made and for the file format.
- `add_card_to_collection(...)` — an almost identical port of what in the TUI was
  `add_card_to_collection_logic` in `ui/app.py`: the same price rule (CardTrader as the sole
  source), the same stack-merge rule (id+set_code+rarity+grade). **Does not save to disk on its
  own** — the caller decides when (same reason as before: Bulk Add queues up several
  additions before a final commit).
- `image_to_data_uri(pil_image) -> str` — encodes a PIL image as base64 PNG that can be
  embedded directly in `<img src="...">`, used by the Grading module.
- `sell_staging: List[SellStagingItem]` — rows under review for selling on CardTrader (see
  the dedicated section below and [06-notes-and-discrepancies.md](06-notes-and-discrepancies.md)). **Purely
  in-memory, never persisted** (unlike `pending_gradings`): it is just a reference to an existing
  `CollectionItem` plus price/condition/quantity not yet confirmed, cheap to
  rebuild — a restart loses unconfirmed staging, the same treatment as `bulk_queue`.
  `add_staging_item`/`get_staging_item`/`remove_staging_item`/`find_staging_item_by_row` are the
  only points that touch it.

## Pattern common to all pages

Every page has:
- A "full" template (e.g. `collection.html`) that extends `base.html` (header, 3-item nav —
  Collection, Add Card, Grading; Bulk Add is reached via a button inside Add
  Card, it has no nav entry of its own, see below —
  `<script src="/static/htmx.min.js">`) and includes an initial partial.
- One or more "partial" templates (prefixed `_`, e.g. `_collection_content.html`,
  `_add_results.html`) that are **both** included in the full page on first load **and**
  returned directly by endpoints called via htmx (`hx-get`/`hx-post` with
  `hx-target`/`hx-swap="outerHTML"`) — the same HTML fragment serves the initial render and
  the subsequent partial update, no markup duplication.

A simplification enabled by the web paradigm compared to the TUI: the old UI had a 2-
step flow with server-side state ("select card" then "select set", cf. `selected_card`/
`selected_set` on `AddCardView`). Here, the search **already returns all cards with all their
sets/rarities listed** (each row has its own mini-form with `card_id`+`set_code` in
hidden fields) — zero "selected" state to keep server-side for this flow. The same pattern is
reused by the Grading→collection linking.

## `web/routers/collection.py` + `templates/collection.html`, `_collection_content.html`

- `GET /` — full page.
- `GET /collection/table?q=&min_price=&sort=&dir=` — called by htmx on every keyup in the
  filter/min-price fields (`hx-trigger="keyup changed delay:300ms"`) and on clicks on column
  headers (which pass `sort`/`dir`, with `dir` computed server-side by a `next_dir` function
  passed to the template to toggle direction).
- `POST /collection/refresh-prices` — re-queries CardTrader for each item, reports how many
  cards found a real price.
- `POST /collection/delete` (form `id`, `set_code`, `rarity`, `grade`) — removes the item that
  matches on all 4 fields (more precise than the old TUI, which matched only on id+set_code —
  an intentional deviation, strictly safer, not a regression).
- `GET /collection/export-csv` — generates and returns `collection.csv` as a download
  (`FileResponse`).
- Table with sortable columns (same set of `SORT_EXTRACTORS` as the old
  `collection_view.py`), aggregate metrics, condition bar — all computed via
  `item.get_price_for_condition(...)`, so they automatically reflect real prices.

## `web/routers/add_card.py` + `templates/add_card.html`, `_add_results.html`, `_add_feedback.html`

- `GET /add` — page with a search form.
- `POST /add/search` (form `query`) → `_add_results.html`: each card found in an expandable
  `<details>` with a table of its sets/rarities, each with an "Add" mini-form carrying
  `card_id`+`set_code`+`rarity`+`qty`.
- `POST /add/confirm` → re-fetches the card by id, finds the right `CardSetInfo`, calls
  `AppState.add_card_to_collection`, saves to disk, returns `_add_feedback.html` (price and
  source, "real CardTrader" or "no price found" badge).

## `web/routers/bulk_add.py` + `templates/bulk_add.html`, `_bulk_current.html`

Reached via a button inside `add_card.html` ("🚀 Bulk Add"), no longer via a
dedicated nav entry — `bulk_page` sets `active_tab="add"` (not `"bulk"`, which no longer exists in
`base.html`) so the "Add Card" tab stays highlighted here too.

- `GET /bulk` — page with a textarea.
- `POST /bulk/load` (form `codes`, separated by space/newline) → builds `AppState.bulk_queue`
  by resolving each code via YGOPRODeck, resets `bulk_index` to 0.
- `POST /bulk/confirm` (form `set_code`, `qty`) / `POST /bulk/skip` — advance
  `AppState.bulk_index` by one, showing via `_bulk_current.html` the current card (with the
  table of its sets, the same pattern as Add Card) or, once the queue is exhausted, the
  added/skipped summary with the final button.
- `POST /bulk/save-all` — `StorageService.save_collection` on the entire in-memory collection
  (including additions staged during the queue).

## `web/routers/grading.py` — single-photo page + Bulk Grading + "pending" inbox

Three flows on the same page (`templates/grading.html`), which share a single "inbox"
(`AppState.pending_gradings`, see [07-grading.md](07-grading.md) for why this
architectural choice was made — linking a card to an entry in the collection is a separate action
from analyzing it, both for a single photo and in bulk):

- **Single photo**: an upload form (native `<input type="file">` — it has entirely replaced the
  old custom TUI `ImagePickerScreen`/`DirectoryTree`) + manual 4-corner cropping
  (`web/static/corner-picker.js`, vanilla JS, with a magnifying loupe during drag) over
  the preview, before analysis can proceed.
- **Bulk**: two `<input type="file" multiple>` fields (one with `webkitdirectory` to select
  an entire folder) build a client-side queue of `File` objects — no server call
  until the first crop is confirmed. A **second, independent instance** of the same
  cropper (`createCornerPicker`, a reusable factory in `corner-picker.js` — two instances on the
  same DOM don't interfere with each other, each has its own "closed" drag state in its own
  closure) shows one photo at a time; "Confirm crop and analyze" makes a manual `fetch()` (not
  htmx — imperative control is needed over "wait for this analysis, then advance") to the same
  `POST /grading/analyze` used for the single photo, then automatically advances to the next
  photo. Once the queue is exhausted, it calls `htmx.ajax("GET", "/grading/pending", ...)` to
  refresh the inbox — the only point where the bulk flow interacts with htmx instead of plain
  `fetch()`.
- **Inbox "📦 Graded cards awaiting linking"** (`_grading_pending.html`): a compact
  list (thumbnail, grade, condition) of each `PendingGrading`, with two actions per row:
  - "🔗 Link" → `GET /grading/pending/{id}/link` (`_grading_pending_link.html`, a search box
    scoped to that id) → `POST /grading/search` (`pending_id` in the form, to
    `_grading_search_results.html`, scoped on `#grading-search-results-{{ pending_id }}` so
    multiple searches open in parallel on different rows don't overwrite each other) →
    `POST /grading/save` (`pending_id` + `card_id`/`set_code`/`rarity`/`qty`) — calls
    `add_card_to_collection`, saves to disk, **removes** that entry from `pending_gradings`, and
    returns the entire updated `_grading_pending.html` (with a confirmation flash) as the new
    `#grading-pending`.
  - "🗑️" → `POST /grading/pending/{id}/discard` (with `hx-confirm` — a native confirmation dialog
    before the request) — removes it without touching the collection.

Technical detail on how the single photo updates the inbox **without a separate request**:
`POST /grading/analyze` returns `_grading_result.html` (the detail view with the two images,
sub-scores, explanation — unchanged) followed by a second block with the same `id="grading-
pending"` but `hx-swap-oob="true"` (htmx's **out-of-band swap**: any element with this
attribute in a response gets applied to the DOM element with the same id, regardless of
the request's `hx-target`) — a single request updates both the detail panel and
the inbox below it. The `oob` flag that drives this attribute in the template comes from
`_pending_context(..., oob=True)` in `grading.py`, `False` for all other uses of the same
partial (page load, after discard/save, where `#grading-pending` is already the direct target and
the attribute is not needed). The bulk flow doesn't need it because it uses plain `fetch()`
(which doesn't process htmx's OOB swaps) and instead calls `htmx.ajax(...)` only once at the end
of the queue.

`_grading_result.html` no longer has its own inline search/link box (removed): after
a single analysis, the card appears in the inbox like any other, the same linking point
for both single photos and bulk.

## `web/routers/sell.py` + `templates/sell.html`, `_sell_page_content.html`, `_sell_staging.html`, `_sell_listings.html`

Bulk and single-item selling share the same flow, following the same architectural model
as the `pending_gradings` inbox (a flat list indexed by id, each row actionable
independently) — not the one-at-a-time cursor of Bulk Add. Full design details in
[06-notes-and-discrepancies.md](06-notes-and-discrepancies.md).

- From the Collection page (`_collection_content.html`): a checkbox column (`name="row_ids"`) +
  a "💰 Sell selected" button (`hx-include="[name='row_ids']:checked"`, the same pattern already
  used to cross-reference the `q`/`min_price` fields with each other) for bulk selling; a
  "💰 Sell" button per row (the same `hx-vals` scheme as the existing Delete button, but with a
  single `row_id`) for selling a single card. Both point to `POST /sell/stage`, which accepts
  either `row_ids` (repeated) or `row_id` (scalar) — the same route for both cases.
- `POST /sell/stage` — for each id: skips it if already in staging or if an `active` listing
  already exists (idempotency). Resolves the blueprint only if
  `CollectionItem.cardtrader_blueprint_id` is not already set (never recalculated otherwise); if
  ambiguous, populates `candidates` on the `SellStagingItem` for disambiguation on the template
  side. Responds with `HX-Redirect: /sell` — the first (and so far only) time the app uses this
  htmx pattern, all other interactions do an in-place swap.
- `POST /sell/staging/{id}/resolve` (form `blueprint_id`) — persists the disambiguation choice
  on the `CollectionItem` and saves it to disk.
- Each row in `_sell_staging.html` also has a "Language" select
  (`config.CARDTRADER_SELL_LANGUAGES`, pre-selected to `config.DEFAULT_SELL_LANGUAGE`) — **not**
  inferred from `set_code` because that is unreliable for this collection (see
  [06-notes-and-discrepancies.md](06-notes-and-discrepancies.md)). `config` is explicitly exposed
  in the context by `_sell_context()` in `sell.py` for this reason — no other template needs it
  today.
- `POST /sell/staging/{id}/remove` — removes a row from staging, no side effects.
- `POST /sell/confirm` — **the only route in the app that reads raw `await request.form()`**
  instead of typed `Form(...)` parameters, because field names are dynamic per row
  (`condition_{id}`/`price_{id}`/`quantity_{id}`, generated by `_sell_staging.html`, which wraps
  the entire table in a single `<form>` — another first for the app, the other pages always use
  bare buttons with `hx-vals`). Tolerant of partial failures: a row with invalid data
  or a CardTrader error stays in staging with the error shown, the others proceed.
  Care is needed when modifying this route: a row's error must be **cleared on every attempt**
  before revalidating, otherwise a past failure blocks subsequent attempts forever
  even after the user fixes the input (a real bug found and fixed during development).
- `POST /sell/listings/{id}/cancel` — `DELETE /products/:id` (via `CardTraderAPI.delete_listing`,
  which treats a 404 as success) + local flip to `cancelled`.
- `POST /sell/listings/sync-prices` — realigns every `active` listing to the current
  suggested price (`get_price_for_condition(condition) * (1 - config.SELL_SUGGESTED_PRICE_DISCOUNT)`)
  via `update_listing_price`, tolerant of per-listing failures. A listing does not
  automatically follow the collection's prices after creation — this exists to resync
  it when they change (price refresh, bug fix, etc.). See
  [06-notes-and-discrepancies.md](06-notes-and-discrepancies.md) for the bug that motivated this
  route.
- `POST /sell/poll-orders` — the only way (manual, no webhook) to detect sales; it polls
  `GET /orders` and cross-references product ids against local `active` listings.
- `/collection/delete` (in `collection.py`) blocks deletion of a stack with an `active`
  listing (`storage.get_active_listing_for_row`), with an explanatory flash instead of proceeding.

## `web/static/style.css`

Hand-written CSS, dark theme (`--bg`, `--panel`, `--accent` etc. as CSS custom properties on
`:root`), no framework. Main classes: `.panel` (bordered box, reused everywhere instead
of the old Textual `box_panel`), `.metric-card`/`.cond-badge` (metrics/conditions bar),
`.grading-images` (the two side-by-side `<figure>`s in Grading, `max-width: 100%` on the `img`s
for the responsive scaling that couldn't be guaranteed in the TUI), `.htmx-indicator` (shown only
while an htmx request is in progress, via the `htmx-request` classes that htmx applies
automatically).
